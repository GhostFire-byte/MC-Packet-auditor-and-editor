4. Packet auditing



The auditor should support the following capabilities.



Live packet inspection



- Capture incoming and outgoing packets.

- Display packets in real time.

- Identify packet direction:

  - CLIENT → SERVER

  - SERVER → CLIENT

- Display packet names.

- Display packet IDs where available.

- Display timestamps.

- Display packet sizes.

- Display protocol state.

- Display decoded packet contents in a structured format.

- Support searchable packet history.

- Support filtering by packet name, ID, direction, size and other available properties.



Packet statistics



- Total packets sent and received.

- Incoming and outgoing bandwidth.

- Packet frequency.

- Data volume.

- Live traffic statistics.

- Chronological packet timeline.

- Timestamps and event markers.



Connection monitoring



Monitor relevant connection events and expose them through the dashboard.



The exact events and metadata should be determined during the technical design phase.



5. Packet editing



Support both structured packet inspection/editing and raw packet inspection/editing.



Structured editor



- Display decoded packet fields.

- Allow supported fields to be modified.

- Validate modified values.

- Show original and modified values.

- Provide before-and-after comparisons.

- Clearly identify unsupported or non-editable fields.



Raw packet viewer/editor



- Provide a readable representation of the serialized packet data.

- Allow supported raw-level modifications.

- Validate modified data before use.

- Clearly distinguish serialized packet data from the decoded Minecraft packet object.



Do not assume that changing displayed raw bytes automatically updates the decoded packet object.



Implement a technically correct conversion, validation and serialization process.



Editing history



- Track packet modifications.

- Record original and modified values.

- Include timestamps.

- Identify the applicable editing rule.

- Allow users to inspect previous modifications.



Packet templates



Support reusable packet templates where technically appropriate.



Editing rules



Allow users to create automatic editing rules for future matching packets.



Rules should support:



- Packet type matching.

- Direction matching.

- Field conditions.

- Replacement values.

- Enable/disable controls.

- Rule priorities.

- Preview before activation.

- Modification history.



6. Packet selection and interaction



Normal packet traffic must continue uninterrupted by default.



Live packet capture should initially be passive.



When I click a packet in the live packet list, display an action menu that lets me choose what to do.



Possible actions include:



- Inspect packet.

- Edit this packet.

- Change all matching future packets.

- Intercept matching future packets.

- Delay matching future packets.

- Discard matching future packets, subject to protection rules.



Important technical distinction:



A packet that has already been transmitted or processed cannot be retroactively intercepted or held.



Actions involving interception, editing, delay or discard must therefore operate on the next eligible packet or subsequent matching packets.



Clearly communicate this distinction in the UI.

Advanced

8. Packet interception and queue management



Support controlled packet interception and holding.



The queue manager should provide:



- FIFO queueing by default.

- Individual packet selection.

- Single-packet release.

- Individual editing before release where supported.

- Individual discard where permitted.

- Batch operations.

- Queue size limits.

- Configurable overflow behaviour.

- Queue status indicators.

- Timeout protection.

- Ordering preservation by default.



The system must distinguish between packets waiting in the interception queue and packets already processed by Minecraft.



Avoid deadlocks and networking-thread starvation.

10. Safety and packet protection



Essential connection-integrity packets must be protected by default.



In particular, PONG and KeepAlive packets must not be accidentally modified or disrupted.



Implement an Advanced Mode switch.



The selected safety policy is:



- Normal Mode protects essential connection-integrity packets.

- Advanced Mode unlocks other supported packet modifications.

- Essential connection-integrity packets remain protected even in Advanced Mode.



Protection must apply consistently across manual editing, automatic rules, delay rules, interception and discard operations.



Do not rely solely on hiding controls in the GUI. Enforce protection in the underlying processing layer.



Display clear explanations when an operation is blocked by a protection rule.
